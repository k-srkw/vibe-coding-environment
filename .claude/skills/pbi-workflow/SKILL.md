# PBI ワークフロー（ATDD + DoD）

PBI の着手から完了まで、Definition of Done に従った ATDD ワークフローを 5 フェーズで実行する。

引数として PBI 番号またはファイル名を受け取る（例: `/pbi-workflow 1` または `/pbi-workflow pbi-01-rhdh-local-setup.md`）。

## Phase 1: 着手準備

1. 指定された PBI ファイルを `docs/product-backlog/` から読み込む
2. ステータスが「未着手」であることを確認する
3. 依存 PBI のステータスがすべて「完了」であることを確認する
4. 依存 PBI の受け入れテストがリグレッションしていないことを確認する

いずれかが未達の場合、着手不可の理由を表示して停止する。

すべて OK の場合:
- PBI ファイルのステータスを「進行中」に更新する
- `docs/product-backlog/README.md` の一覧テーブルも「進行中」に更新する

## Phase 2: テスト先行（ATDD）

1. 受け入れ条件を 1 つずつ確認する
2. 各受け入れ条件に対して:
   - Gherkin シナリオに変換できるもの → `.feature` ファイルを作成する
   - テストが書けないもの → 手動確認手順を明記する
3. PBI ファイルの「受け入れ条件の検証方法」テーブルを埋める
4. ユーザーに `.feature` ファイルと検証方法テーブルの確認を求める

この時点ではステップ定義は未実装で OK。テストは Red（失敗）の状態。

## Phase 3: 実装

### ステップ 1: 実装計画（メインセッション）

Plan モードで実装計画を立て、ユーザーと合意する。

### ステップ 2: サブエージェントによる実装 + リファクタリング

Plan 確定後、`Agent` ツールで **1 つのサブエージェント** を起動し、実装とリファクタリングを委譲する。

サブエージェントのプロンプトには以下を含めること:

1. **確定した実装計画の全文**
2. **PBI ファイルのパスと受け入れ条件**
3. **Phase 2 で作成した `.feature` ファイルのパス一覧**
4. **テスト実行コマンド**: `npm test`
5. **実装の指示**:
   - Gherkin シナリオに対応するステップ定義と実装コードを作成する
   - `npm test` でテストを実行する
   - テストが全件 Green になるまで実装を繰り返す
6. **リファクタリングの指示**（全テスト Green 達成後に実施）:
   - 実装コードの観点: 重複コードの共通化、責務分離、命名改善、マジックナンバーの定数化、不要コードの除去、エラーハンドリングの整理
   - テストコードの観点: Gherkin の可読性向上、ステップ定義の重複排除、テストデータのハードコード排除（Scenario Outline / Examples 活用）、ヘルパー・フィクスチャの共通化
   - リファクタリングは「振る舞いを変えない変更」に限定する
   - 各変更のあとに `npm test` を実行し、全テスト Green を維持する
   - テストが Red になった場合はリファクタリングを取り消し、より小さな単位でやり直す
7. **全体制約**: 実装・リファクタリングを通じて `npm test` が全件 Green の状態を維持すること

プロンプトの例:

```
以下の実装計画に従い、PBI の実装とリファクタリングを行ってください。

## 実装計画
{確定した計画の全文}

## コンテキスト
- PBI ファイル: {PBI ファイルのパス}
- Feature ファイル: {.feature ファイルのパス一覧}
- テスト実行: `npm test`

## 実装タスク
1. Feature ファイルの Gherkin シナリオに対応するステップ定義と実装コードを作成してください
2. `npm test` を実行し、全テストが Green になるまで修正を繰り返してください

## リファクタリングタスク（全テスト Green 達成後）
全テスト Green を維持しながら、以下の観点でコード品質を改善してください:
- 実装コード: 重複の共通化、責務分離、命名改善、定数化、不要コード除去
- テストコード: Gherkin の可読性、ステップ定義の再利用性、テストデータの外部化
各変更後に `npm test` を実行し、Red になったら取り消して小さな単位でやり直してください。
リファクタリングは「振る舞いを変えない変更」に限定してください。

## 制約
- 全工程を通じて `npm test` が全件 Green であること
```

## Phase 4: 結果確認

サブエージェント完了後、メインセッションで以下を確認する:

1. `npm test` を実行して全テスト Green を確認する
2. 変更差分をレビューする
3. 問題があれば修正を指示する（サブエージェント再起動 or メインセッションで対応）

## Phase 5: 完了判定（DoD チェック）

`docs/product-backlog/definition-of-done.md` を読み込み、以下を順番にチェックする:

### 1. ATDD サイクル
- [ ] 受け入れ条件に対応する Gherkin シナリオが存在する（または手動確認として登録済み）
- [ ] テストが全件 Green（テスト環境がある場合）

### 2. 受け入れ条件
- [ ] PBI ファイルの受け入れ条件が全件 `- [x]` チェック済み
- [ ] 検証方法テーブルが埋まっている

### 3. 成果物
- [ ] 「想定する成果物」のファイルがすべて存在する

### 4. リグレッション
- [ ] 既完了 PBI のテストが引き続き Green

### 5. コンテキスト更新
以下を実行する:
- PBI ファイルのステータスを「完了」に更新する
- `docs/product-backlog/README.md` の一覧テーブルを更新する
- 実装で得た知見があれば CLAUDE.md または関連ドキュメントに追記する

### 6. 完了証跡
PBI ファイルの「完了証跡」セクションに以下を記録する:
- テスト実行結果（シナリオ数、ステップ数、pass/fail）
- 確認日時
- 備考（手動確認した項目の結果等）

### 7. ADR（意思決定記録）

実装中に行った設計判断を振り返り、ADR として記録する:

1. Phase 2〜4 で行った意思決定（技術選定、設計方針、トレードオフ等）を洗い出す
2. 記録すべき判断がある場合:
   - `docs/adr/adr-template.md` をもとに ADR ファイルを `docs/adr/` に作成する
   - ファイル名は `NNNN-kebab-case-title.md`（連番）
   - `docs/adr/README.md` の一覧テーブルに追加する
3. 記録すべき判断がない場合はスキップする（軽微な PBI では ADR なしも OK）
4. PBI ファイルの完了証跡セクションに、関連 ADR のリンクを記載する
5. ADR を作成しない場合も、完了証跡の「ADR」欄に要否判断の理由を記録する（例: 「設計判断は軽微のため ADR なし」「既存パターンの踏襲のみのため不要」）

すべて OK の場合のみ、PBI を「完了」とする。NG がある場合は未達項目を一覧表示して停止する。
