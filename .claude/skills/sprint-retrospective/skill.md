# スプリントレトロスペクティブ → 改善 PBI 作成

スプリント完了後にレトロスペクティブを実施し、Keep / Problem / Try を整理した上で、改善項目を PBI としてバックログに登録する。

引数としてレトロスペクティブの観点を受け取る（例: `/sprint-retrospective 開発ワークフロー、アーキテクチャ、テスト妥当性`）。観点が指定されない場合は以下のデフォルト 3 観点を使用する:

- 開発ワークフロー・Agent ワークフロー・SDLC
- アーキテクチャ
- テスト妥当性

## Phase 1: データ収集

Explore エージェントを **2 つ並列**で起動し、raw data を収集する。エージェントの役割はファクトの収集であり、ユーザー指定の観点に沿った整理は Phase 2 で行う。

### エージェント 1: 開発プロセスの分析

- `git log --oneline --all` でコミット履歴を取得
- 各 PBI ファイル（`docs/product-backlog/pbi-*.md`）のステータス・受け入れ条件・完了証跡を確認
- `docs/product-backlog/definition-of-done.md` との準拠状況を評価
- ADR（`docs/adr/`）の記録状況を確認
- PBI ワークフロースキル（`.claude/skills/pbi-workflow/`）の運用実態を確認
- **過去のレトロスペクティブ文書**（`docs/sprint-*-retrospective.md`）を読み、前回の Problem/Try の進捗を把握する

### エージェント 2: アーキテクチャとテスト品質の分析

- ディレクトリ構造とモジュール依存関係をマッピング
- 全 `.feature` ファイルのテスト種別を分類（ファイル存在 / 静的内容 / 動的行動 / E2E 統合）
- ステップ定義のアサーションパターンを評価
- テストカバレッジのギャップを特定
- `skeleton/` の品質（生成プロジェクトが実際に動作するか）を評価
- `.claude/` ディレクトリ（スキル、設定ファイル）のコンテキストエンジニアリング品質を評価

## Phase 2: レトロスペクティブ整理

収集した raw data を、ユーザー指定の各観点に沿って **Keep / Problem / Try** に整理する。

### 各項目の基準

- **Keep**: 今回うまくいったこと。具体的な証拠（コミット数、テスト数、DoD 準拠率など）を添える
- **Problem**: 改善すべき課題。影響範囲とリスクを明記する
- **Try**: 次スプリントで試すこと。Problem に対する具体的なアクションを記述する

### 既存 PBI との照合（重要）

Problem / Try を整理する際に、既存の未着手 PBI と照合し、重複を特定する。各 Problem に対して「新規 PBI が必要」か「既存 PBI で対応済み」かを判定し、**対応 PBI** 列に記録する。これにより重複 PBI の作成を防ぐ。

### 出力形式

各観点ごとに以下の形式で整理する:

**Keep テーブル:**
```markdown
| # | 項目 | 根拠 |
|---|------|------|
| K1 | ... | ... |
```

**Problem → Try テーブル（対応 PBI 列を含む）:**
```markdown
| # | Problem | 影響 | Try | 対応 PBI |
|---|---------|------|-----|---------|
| P1 | ... | ... | ... | **PBI-NN**（新規）or **PBI-NN**（既存） |
```

末尾にメトリクスサマリー（PBI 完了数、テスト数、ADR 数、テスト種別比率など）をテーブル形式で付ける。

### ユーザー確認

整理した結果をユーザーに提示し、AskUserQuestion で以下の 3 点を **一括で** 確認する:

1. 追加すべき観点や見落としがないか
2. Problem の優先度に異論がないか
3. PBI 化する改善項目の選定（全て / 高優先度のみ / 個別選択）

同時に PBI 分割方針も確認する:

- 項目ごとに個別 PBI
- カテゴリごとにまとめる
- 大小で分ける（軽微な修正をまとめて 1 PBI に）

## Phase 3: 改善 PBI の作成

ユーザーが承認した Problem / Try 項目のうち、**既存 PBI で対応済みでないもの**を PBI に変換する。

### PBI ファイルの作成

各 PBI を `docs/product-backlog/pbi-NN-xxx.md` として作成する。既存 PBI の最大番号の続きから採番する。

PBI ファイルのフォーマットは既存 PBI のテンプレートに従う:

```markdown
# PBI-NN: タイトル

## ステータス: 未着手

## 依存
- なし（または依存 PBI へのリンク）

## 説明
レトロスペクティブのどの Problem に対応するかを明記する。

## 受け入れ条件
- [ ] 条件 1
- [ ] 条件 2

## 受け入れ条件の検証方法
| 受け入れ条件 | 検証方法 | 対応するシナリオ |
|-------------|---------|----------------|
| <!-- 着手時に記入 --> | | |

## 想定する成果物
- ファイル名

## 完了証跡
<!-- PBI 完了時に記入。このセクションが空の状態で「完了」にしてはならない -->
- テスト実行結果:
- 確認日時:
- 備考:
```

### バックログ更新

`docs/product-backlog/README.md` の PBI 一覧テーブルに新規 PBI を追加する。スプリント区切り（見出し）をつけて既存 PBI と分離する。

## Phase 4: レトロスペクティブ文書の保存

レトロスペクティブの結果を `docs/sprint-N-retrospective.md` として保存する。N は `docs/sprint-*-retrospective.md` の連番に従う。

### 文書構造

以下の標準構造で保存する:

```markdown
# Sprint N レトロスペクティブ

- 実施日: YYYY-MM-DD
- 対象期間: ...
- 観点: 観点1、観点2、観点3

## 観点 1: タイトル

### Keep
（テーブル形式: # / 項目 / 根拠）

### Problem → Try
（テーブル形式: # / Problem / 影響 / Try / 対応 PBI）

---

## 観点 2: タイトル
（同上）

---

## メトリクスサマリー
（テーブル形式: メトリクス / 値 / 備考）

## 改善 PBI 一覧

### 新規作成
（テーブル形式: # / PBI / カテゴリ）

### 既存 PBI で対応済み
（テーブル形式: Problem / 対応 PBI）
```
