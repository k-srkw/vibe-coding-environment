## 1. 開発ワークフロー・Agent ワークフロー・SDLC

### Keep（継続すべきこと）

**ATDD ワークフローの徹底**
- 全 9 PBI で「Feature ファイル先行 → 実装 → DoD チェック」のサイクルが厳守された
- 受け入れ条件と Gherkin シナリオの 1:1 対応、検証方法テーブルの記入、完了証跡の記録がすべて完遂
- テスト数は単調増加（4 → 8 → 12 → 16 → 22 → 30 → 35 → 39 → 42）でリグレッションゼロ

**サブエージェント委譲パターンの有効性**
- Phase 3 でサブエージェントに実装+リファクタリングを委譲するパターンにより、PBI-3〜6 を約 2 時間、PBI-7〜9 を約 1.5 時間で完了
- 1 PBI = 1 コミットの粒度が明確で、各コミットに全テスト Green の証跡がある

**DoD の機能**
- 7 項目の DoD チェックリストが形骸化せず、全 PBI で実質的に機能した
- 特に「完了証跡セクションが空の状態で完了にしてはならない」ルールが品質ゲートとして有効

### Problem（改善すべきこと）

**Phase 番号の欠番**
- PBI ワークフロースキルの Phase が 1→2→3→5 と飛んでおり、Phase 4 が存在しない
- 次スプリントまでに番号を修正するか、Phase 4 を明示的に定義すべき

**1 PBI = 1 スカッシュコミットで Red→Green→Refactor の履歴が消失**
- サブエージェントの作業がすべて 1 コミットに集約されるため、ATDD の Red→Green→Refactor サイクルの過程が git 履歴に残らない
- 学習・監査目的で中間コミットを保持するか、サブエージェントのログを別途保存することを検討すべき

**ブランチ戦略の不在**
- 全 21 コミットが main ブランチに直接コミットされている
- テンプレートが生成するプロジェクトでは PR ベースのワークフローを推奨しているのに、本リポジトリ自体はその実践がない
- MVP フェーズでは許容されるが、今後は feature ブランチ + PR を採用すべき

**PBI-5, PBI-6 で ADR 検討の明示的記録がない**
- PBI-3, 4, 7, 8 は「新たな設計判断なし」と明記しているが、PBI-5, 6 は言及がない
- ADR 要否の判断自体を記録する運用を徹底すべき

### Try（次に試すこと）

- サブエージェントに中間コミット（Red→Green→Refactor 各段階）を作成させ、最終コミットのみ main に squash merge する運用
- PBI ワークフロースキルに Phase 4（レビュー/差分確認）を追加し、番号欠番を解消
- 各 PBI の完了証跡に ADR 要否判断の一文を必須化

## 2. アーキテクチャ

### Keep

**テストサポートインフラの設計**
- 8 つのサポートモジュール（551 行）が関心ごとに分離されており、循環依存がない
  - `constants.ts`: パス・URL・タイムアウトの一元管理
  - `skeleton-helpers.ts`: テンプレート変数置換・クリーン環境構築
  - `scaffolder-helpers.ts`: Scaffolder API 操作
  - `github-helpers.ts`: GitHub API 操作
  - `rhdh-helpers.ts`: RHDH 操作（コンテナ制御、ゲストログイン、トークン取得）
  - `rhdh-template-helper.ts`: テンプレート登録の冪等性保証
- 各モジュールは `constants.ts` のみに依存し、相互依存がない（`rhdh-template-helper.ts` → `rhdh-helpers.ts` のみ例外）

**skeleton の品質**
- 生成されるプロジェクトは `npm install && npm test` で即座に動作する
- `CLAUDE.md`（128 行）が充実しており、コーディング規約・ATDD ワークフロー・PR ルールを網羅
- `atdd-sample.feature` が Scenario Outline、Background、タグの実践的なサンプルを提供
- `verify-setup.sh` が GitHub Actions ジョブサマリー出力対応の本番品質

**ADR による設計判断の記録**
- ADR-0001（RHDH Local clone 方式）、ADR-0002（app-config.local.yaml 方式）、ADR-0003（lockfile + コピー検出）
- いずれも Context に代替案、Decision に理由、Consequences にトレードオフが記載

### Problem

**`workflow-state.ts` の共有ミュータブル状態**
- モジュールレベルの `let workflow: Workflow` 変数を複数のステップファイルが共有している
- playwright-bdd がフィーチャーを分離実行するため現時点では問題ないが、テスト実行順序の変更やワーカー数変更で干渉リスクがある
- Playwright fixture（テスト単位のスコープ）に移行すべき

**skeleton の `CLAUDE.md` が `src/` ディレクトリを参照しているが、実体がない**
- ディレクトリ構造の説明に `src/` が記載されているが、skeleton に `src/` は存在しない
- 生成されたプロジェクトを受け取った開発者が混乱する可能性がある

**`rhdh-local/` の `.gitignore` による脆弱性**
- RHDH Local は clone して使う設計だが、`app-config.local.yaml` に GitHub PAT が書き込まれる
- `.gitignore` で本リポジトリには含まれないが、`rhdh-local/` 自体の git に残る可能性がある
- 環境変数や Docker secret で管理すべき

**潜在的に ADR が必要だった判断**
- PBI-4: `@cucumber/cucumber` から `playwright-bdd` への技術変更（PBI 当初計画からの変更）
- PBI-6: GitHub Actions ワークフローの静的解析 vs 実行時検証の方針

### Try

- `workflow-state.ts` を Playwright fixture ベースに移行
- skeleton の `CLAUDE.md` から `src/` 参照を削除、または空の `src/` ディレクトリを追加
- RHDH Local の認証情報管理を環境変数ベースに統一

## 3. テスト妥当性

### Keep

**動的行動テストの設計パターン**
- skeleton を一時ディレクトリに展開 → Nunjucks 変数置換 → `npm install` → `npm test` 実行（`cucumber-gherkin-structure.steps.ts`）
- `verify-setup.sh` の成功/失敗パステスト（`setup-verification.steps.ts`）
- RHDH ブラウザ統合テスト: Playwright でゲストログイン → テンプレート一覧表示 → パラメータ入力確認
- Scaffolder API E2E テスト: テンプレート実行 → GitHub リポジトリ作成 → ファイル構成検証 → クリーンアップ

**手動確認と自動テストの明確な分類**
- 検証方法テーブルで「自動テスト」と「手動確認」を分離し、手動項目には具体的な確認手順を記載
- PBI-9 では 54 行の手動テスト手順書と結果記録テーブルを作成

### Problem

**テスト種別の偏り: 構造検証が 77%、行動検証が 23%**

| テスト種別 | シナリオ数 | 割合 | 例 |
|-----------|-----------|------|-----|
| ファイル存在確認 | ~15 | 35% | `fs.existsSync(path)` |
| 静的内容検査 | ~18 | 42% | `content.toContain('keyword')` |
| 動的行動テスト | ~7 | 16% | skeleton npm test 実行、verify-setup.sh 実行 |
| E2E 統合 | ~3 | 7% | Scaffolder API → GitHub repo 作成 |

構造検証（ファイル存在 + 静的内容 = 77%）は「テンプレートが正しいファイルを生成する」ことを保証するが、「生成された環境が実際に機能する」ことの保証は動的テスト（23%）に限られる。

**カバレッジギャップ**

| 未テスト領域 | リスク |
|-------------|--------|
| テンプレートパラメータの境界値（空文字、特殊文字、日本語） | テンプレート実行が予期しないファイル名で失敗する |
| 生成された CI ワークフローの実行検証 | ワークフロー構文エラーが本番で発覚する |
| `catalog-info.yaml` のレンダリング結果の妥当性 | Backstage カタログ登録が失敗する |
| テンプレート再実行（同名リポジトリ）の挙動 | 冪等性がなく、ユーザーが混乱する |
| skeleton のネガティブテスト（壊れた TypeScript 等） | エラーハンドリングの品質が不明 |

**`@github` テストのゲーティング問題**
- E2E 統合テスト（最も価値の高いテスト）が `GITHUB_TOKEN` 未設定時にスキップされる
- ローカル開発での `npm test` では常にスキップされ、実質的に CI でしか実行されない
- テストの価値が最も高い部分が最も実行されにくい構造

### Try

**テスト投資の重心を行動テストに移す**
- 構造検証は十分に蓄積されており、追加の「ファイルに文字列 X が含まれる」テストは収穫逓減
- 次スプリントでは以下を優先:
  1. テンプレートパラメータの Scenario Outline テスト（境界値・特殊文字）
  2. 生成プロジェクトの TypeScript コンパイル・テスト実行の自動検証
  3. `catalog-info.yaml` の Backstage 互換性検証

**`@github` テストの実行頻度向上**
- CI パイプラインで `GITHUB_TOKEN` を secret として設定し、PR マージ前に E2E テストを実行する運用を検討
