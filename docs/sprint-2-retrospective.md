## 観点 1: PBI の並列作業

### Keep

| # | 項目 | 根拠 |
|---|------|------|
| K1 | Sprint 1 の依存関係グラフが並列性を考慮して設計された | PBI-3/4 は PBI-2 のみに依存し独立実行可能。実際に 25 分差でコミット完了 |
| K2 | Sprint 2 PBI は全て依存なしで設計されている | PBI-10〜17 は「任意の順序で着手可能」と明示。並列作業を前提とした設計 |
| K3 | PBI ファイルが自己完結型のコンテキスト単位として機能 | 各 PBI にステータス・AC・検証方法・成果物・証跡が含まれ、他 PBI を参照せず着手可能 |

### Problem → Try

| # | Problem | 影響 | Try | 対応 PBI |
|---|---------|------|-----|---------|
| P1 | 全 23 コミットが main ブランチ直接コミット — ブランチ戦略がなく、並列作業時にコンフリクトリスクがある | 複数 PBI を同時実装する際に変更が競合し、リグレッションの原因になりうる | Feature branch + PR ワークフローを導入し、並列 PBI 作業を安全にする | **PBI-18** |
| P2 | Sub-agent は逐次実行で、複数 PBI の同時実装を行っていない | Sprint 1 では 9 PBI を 1 つずつ順番に実装。並列可能な PBI-3/4 も実質的に順次作業 | PBI ワークフロースキルに「並列実装モード」を追加し、独立 PBI を同時に sub-agent 委任できるようにする | **PBI-19** |
| P3 | PBI 間のインテグレーション検証がテンプレート自体の CI で自動化されていない | 個別 PBI のテストは通るが、統合時のリグレッション検出が手動に依存 | テンプレートプロジェクトに CI を追加し、PBI マージ時に全テスト自動実行する | **PBI-20** |

## 観点 2: ハーネスエンジニアリング

### Keep

| # | 項目 | 根拠 |
|---|------|------|
| K1 | PBI ワークフロースキルの ATDD 規律が 9/9 PBI で維持された | Feature ファイル先行 → ステップ定義 → 実装 → DoD チェックの一貫した流れ。DoD 準拠率 96% |
| K2 | テスト基盤モジュールの分離設計 | 9 モジュール（552 行）が constants.ts のみに依存する低結合アーキテクチャ |
| K3 | テスト数が単調増加しリグレッションゼロ | 4 → 8 → 12 → 16 → 22 → 30 → 35 → 39 → 42 シナリオ。一度も減少なし |
| K4 | DoD の 8 ステップチェックリストが品質ゲートとして有効に機能 | 完了証跡の強制記録、CLAUDE.md 更新、ADR 検討が漏れなく実施された |

### Problem → Try

| # | Problem | 影響 | Try | 対応 PBI |
|---|---------|------|-----|---------|
| P1 | テンプレートプロジェクト自体に CI/CD がない — 42 テストが自動実行されていない | コミット時のリグレッション検出が手動 `npm test` に依存。見落とし・Skip リスク | GitHub Actions ワークフローを追加し、PR/push 時に全テスト自動実行する | **PBI-20** |
| P2 | 構造テスト 76% vs 行動テスト 24% — 静的検証に偏っている | 「ファイルが存在する」「中身が一致する」テストばかりで、テンプレートの動的動作の検証が手薄 | 行動テスト比率を 50% 以上に引き上げ、テンプレート変数展開やエッジケースの検証を追加 | **PBI-16**（既存） |
| P3 | workflow-state.ts の共有可変状態がテスト間の結合を生んでいる | テストの独立性が低下し、実行順序に依存するバグのリスク | Playwright fixture パターンに移行し、テストごとに独立した状態管理にする | **PBI-12**（既存） |
| P4 | skeleton CI テンプレートに `playwright install` が欠落 | 生成プロジェクトの CI が Playwright ブラウザ未インストールで失敗する可能性 | skeleton の CI ワークフローに `npx playwright install --with-deps` ステップを追加 | **PBI-21** |
| P5 | @github E2E テストが最も価値が高いのに実行頻度が最低 | トークン/インフラ制約によりゲートされており、最も重要な検証が最も弱い | CI 環境での @github テスト自動実行を整備する | **PBI-17**（既存） |

## 観点 3: コンテキストエンジニアリング

### Keep

| # | 項目 | 根拠 |
|---|------|------|
| K1 | CLAUDE.md に DoD ルールと禁止事項が組み込まれ、強制力がある | 「例外は認めない」の明示、3 つの禁止事項により、PBI 完了品質が一定水準を保っている |
| K2 | 3 つのカスタムスキルが一貫した SDLC ツールチェーンを形成 | product-backlog-guide → pbi-workflow → sprint-retrospective が PDCA サイクルを構成 |
| K3 | skeleton の CLAUDE.md（127 行）が生成プロジェクト向けの包括的コンテキストを提供 | コードスタイル、ATDD ワークフロー手順、テストパターン例、PR ルールまで網羅 |
| K4 | Sub-agent 委任プロンプト（Phase 3）が 7 要素の構造化コンテキスト注入パターンを持つ | 実装計画、PBI パス、feature ファイルパス、テストコマンドなど必要情報が漏れなく渡される |
| K5 | ADR によるアーキテクチャ決定コンテキストの永続化 | 3 件の ADR が代替案・トレードオフ付きで記録され、将来の判断に活用可能 |

### Problem → Try

| # | Problem | 影響 | Try | 対応 PBI |
|---|---------|------|-----|---------|
| P1 | ルート CLAUDE.md にプロジェクトアーキテクチャの説明がない | Claude Code が新しい PBI に着手する際、テスト基盤の構成（9 モジュール、552 行）を都度探索する必要がある | CLAUDE.md にアーキテクチャ概要セクション（ディレクトリ構造、テスト基盤モジュール一覧）を追加 | **PBI-22** |
| P2 | skeleton CLAUDE.md が存在しない `src/` ディレクトリを参照 | 生成プロジェクトで Claude Code が誤ったディレクトリ構造を前提にコード生成するリスク | src/ 参照を実際のディレクトリ構造に修正する | **PBI-13**（既存） |
| P3 | settings.local.json にデバッグセッションの残骸が残っている | python3 ワンライナー 2 件がノイズとして許可リストに残存。セキュリティポリシーの意図を曇らせる | settings.local.json をクリーンアップし、意図的な許可のみ残す | **PBI-23** |
| P4 | PBI-5, PBI-6 で ADR 要否判断の記録が欠落 | 設計判断のコンテキストが失われ、将来の変更時に「なぜこうなったか」が追えない | DoD チェックで ADR 要否判断の記録を必須化する | **PBI-11**（既存） |
| P5 | PBI ワークフロースキルの Phase 番号ギャップ（1-2-3-5） | 認知負荷が増加し、ワークフローの理解を妨げる | Phase 4 を追加し連番にする | **PBI-10**（既存） |
| P6 | スキル間のコンテキスト共有メカニズムがない | 各スキルが独立して動作し、前スキルの出力を次スキルに自動的に引き継げない | スキル間で共有可能な構造化出力フォーマットを設計し、SDLC パイプラインとしての連携を強化する | **PBI-24** |
